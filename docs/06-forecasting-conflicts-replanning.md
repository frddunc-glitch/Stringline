# 06 — Forecasting, Conflict Detection and Re-planning

## 1. Working plan
- `WorkingPlan = Apply(WTT, commands[0..n])` — deterministic, so undo/redo is "drop the last command and rebuild" (rebuild is cheap; cache per-train if needed).
- Commands (all implement `IPlanCommand`, serialisable to the session DB):
  - `ShiftTrain(train, fromIndex, deltaSeconds)`
  - `SetDwell(train, index, departTime)`
  - `ChangePlatform(train, index, platform)` / `ChangeLine(train, index, line)`
  - `SkipStop(train, index)` / `AddStop(train, index, dwell)`
  - `TerminateAt(train, index)` / `CancelTrain(train)` / `ReinstateTrain(train)`
  - `CloneTrain(source, newHeadcode, deltaSeconds)`
  - `AddDisruption(d)` / `RemoveDisruption(id)` / `EditDisruption(...)`
  - `AddNote(n)` / `EditNote(n)` / `RemoveNote(id)` (S13)
  - `LinkLiveTrain(simUid, trainId)` (session-level, not a plan change)
  - `ExpectToRun(train, run = true)` (S34): run a train the start rules (§2) say SimSig will not; like a link, not a change to the train's plan, but undone and saved like one
  - `AcceptSuggestion(suggestionId, commands[])` — a composite
- Validation on apply: times monotonic; run time between points ≥ min run time (× disruption factor); depart ≥ arrive. Violations clamp and return a warning shown to the user.

*Implemented in S10 (`Stringline.Planning`):* `WorkingPlan` (immutable: `TrainPlan`s, disruptions, live links), `WorkingPlanBuilder` (validation), the commands above plus `UnlinkLiveTrain`, `PlanCommandJson`, and `PlanningEngine` with undo/redo publishing `PlanSnapshot`s. The rules:
- **Points are never added or removed.** A command's index is the WTT point index. `SkipStop` turns an intermediate stop into a pass at its arrival time; `AddStop` turns a pass into a stop arriving at the pass time. `TerminateAt` keeps the points it no longer runs to (`RunningPoints` ends with a terminating stop), so `ReinstateTrain` (which clears a cancellation and a short termination) brings them back.
- **Minimum run time** (Fred): the fastest booked run between two locations by any WTT train, either way, less the allowances booked between them (`MinRunTable`). Across untimed points, the steps are summed (or the direct pair is used). A pair no train runs directly has no minimum, so only order is kept.
- **Clamping:** only a run or dwell that the command *shortens* is checked, so a WTT that is already tighter than the table elsewhere is left as booked. A run below the minimum moves the point (and its dwell) later; a departure before the arrival moves to the arrival. Each clamp is a `PlanWarning`. A moved point shortens the next run, which is then checked in turn, so a later departure pushes the train on only as far as it must (it uses its slack).
- **Disruptions** (S10 model, S13 UI): a speed restriction lengthens the minimum (`× factor + added`) for runs between calls at its two ends that depart while it is in force, on its track (below). A block never clamps (it becomes a conflict, S14). Adding or editing a disruption does not re-plan trains already in the plan.
- **Tracks** (Fred, S13; `Disruption.AppliesTo`): a disruption with no track covers all lines. A track with a `Direction` is a corridor track: Down applies to trains running from `From` to `To`, Up the other way, BiDirectional (a single line) both; the shell stores `From` as the end nearer the corridor's Up end, so these are the corridor's directions. A track without one is a WTT line code, matched (ignoring case) against the train's planned line out of the point the run starts from. At one location (`From` = `To`) a direction applies to every train. Speed restrictions, blocks and the plan's clamping all use this rule.
- **Notes** (S13, DIS-3): `PlanNote(Id, Location, Time, Text)`, added, changed and removed by `AddNote`, `EditNote` and `RemoveNote`, so they undo with the plan. They change no train and no forecast. IDs come from `WorkingPlan.NewNoteId` (`N1`…) and disruptions' from `NewDisruptionId` (`B1`… for blocks, `SR1`… for restrictions).
- **Clones** take the source's current plan, with the new headcode, moved by the delta, not cancelled. The new `TrainId` is in the command (`WorkingPlan.NewCloneId` gives `{headcode}#c1`, `#c2`…), so a replay gives the same train.
- **Live links are commands** (Fred), so they undo. The engine rebuilds the live state with the plan's links whenever they change. Only WTT trains can be linked.
- **A command that fails changes nothing**, and is not added to the history. A suggestion is all-or-nothing.
- **`ResetTrain`** (S12, "Reset to WTT") puts a WTT train back as booked: times, platforms, lines, not cancelled or terminated short. A clone cannot be reset; a train as booked is refused.
- **History:** undo drops the last command and replays the rest over the WTT; a new command clears redo. Reloading the same timetable (same area and name) replays the history and drops commands that no longer apply; a different timetable, or `Clear`, starts a new history.

## 2. Forecaster (per corridor network, not per graph)

Inputs: working plan, live actuals, clock, section min run times, disruptions, headways.

Algorithm v1 (deterministic, priority-aware, single pass with event queue):
1. For each active train, start state = last actual event (location, time, action). For trains not yet entered, start = planned entry time + `train_delay` hint if any.
2. For each subsequent planned point: `earliest = prevDepart + max(plannedRun, minRun × factor + added)`. Arrival forecast = `max(earliest, ...)`; departure = `max(arrival + minDwell, plannedDepart)` (trains don't leave early from stops; may recover on run allowances).
3. Recovery: a late train runs at min run time (uses up allowances) until back on plan.
4. **Interaction pass (optional toggle, default on):** process all train-section entries in time order via a priority queue; if the section/track is occupied within headway by another train, delay the entry (single line: opposing occupancy blocks the whole section). Ties broken by priority then planned order. This yields "knock-on" forecasts and is where conflicts become *visible delays* rather than overlaps.
5. Trains with no location for > X min of sim time beyond their forecast are flagged "possibly stopped" (feeds disruption hints).

Performance target: 500 trains × 40 points = 20k events → well under 50 ms in C#.

*Implemented in S11 (`Stringline.Planning`):* `Forecaster.Run(ForecastRequest)` → `Forecast` (a `TrainForecast` per train: `ForecastPoint`s with a basis of Actual, Arrived, Forecast or None, a status, `PossiblyStopped`, `KnockOnSeconds`). `ForecastNetwork` holds the sections the interaction pass works on. `PlanningEngine` re-forecasts whenever the live state, the plan or the forecast settings change, and publishes the result in `PlanSnapshot.Forecast`. The rules:
- **One event queue for both passes.** Each train's next departure is queued by time, then category priority (higher first), then plan order. Taking a departure works out the run to the next timed point. With the interaction pass off, the result is the independent forecast (steps 1–3). With it on, the same pass also checks each run against the trains already through its sections. `KnockOnSeconds` is the difference at the last point.
- **Start.** A matched live working's timing-point actuals are mapped onto its plan points in order. Reports at locations the plan does not book are not plan points (SimSig reports every timing location), but see *Unbooked anchors* below. From the latest one: having arrived, the train leaves after the dwell (and not before now); having left or passed, it is on its way. A working whose live train has moved on to its next working is finished. A train not seen starts at its planned time, plus the sim's `train_delay` for its headcode (the first train not started with that headcode), and not before now.
- **Unbooked anchors** (S36, #17; `TrainForecast.Anchor`, `ProgressAnchor`). A report at a timing location the plan does not go to at all, after the train's last booked report, is a progress anchor for the run on to the next timed point, if it lies on the way: between two of the plan's points of that run on a corridor (in that order), or where some WTT train runs from one through it to the other (`LocationGraph.Through`, with skipped timing locations put back). The latest such report wins. Its **share** of the run is the corridor sections' minimum runs that way (from one point to it, over the whole); off the corridors, the WTT's minimums either side of it. The rest of the run takes the WTT's fastest run from it (`MinRunTable`, lengthened by a speed restriction in proportion), else the run's minimum times the share left; and, as for a whole run, no more than the planned rest (the planned run times the share left) or the time to the planned arrival, whichever is less. So a late train that has made up time to the anchor is forecast from there, and an on-time one still does not arrive early. No delay is measured at the anchor (it has no booked time); the hover says "Passed EARLSFD 09:12 (not booked)". A train that arrived at a stop and then reports an anchor has left without reporting its departure: its point keeps only the arrival, and the run is forecast from the anchor. `ForecastOptions.UnbookedAnchors` (on) turns this off for comparison. On Waterloo's 4× recording one headway conflict appears with it (5F89/1P17 at EARLSFD: 1P17 is a minute late just ahead).
- **Formed trains.** A train formed from another (next working, divide, detach, drop) starts no earlier than that train reaches the point where it forms it, plus the turnaround: the WTT's terminate dwell for a next working, divide dwell for a divide, else 30 s. A forming train that will never get there (cancelled, terminated short, or failed) lets it start as planned.
- **Run** = the planned run, or less if the train is late, but never less than the minimum run (`MinRunTable`, lengthened by a speed restriction in force, or the planned run if no minimum is known). It never brings the train in before its planned time: `max(min, min(planned run, planned arrival − departure))`. So a late train uses up its allowances until it is back on time, and an early one stays early only where it passes.
- **Dwell** at a stop: the WTT point's dwell, else the train's (or its category's) station dwell, else 30 s (Fred); never before the planned departure. A pass has none.
- **Now.** No forecast time is before now. A running train not yet reported at its next point is forecast to reach it now. It is `PossiblyStopped` if that is more than 5 min (Fred) past both its forecast and its last report (a report at a signal counts, so a train creeping along a long section is not flagged).
- **Disruptions.** A speed restriction lengthens the minimum, as in S10. A block covering the run while it would run holds the train at its departure point until the block ends, if it applies to the train's track (§1, S13).
- **Progress at learned places** (S38, #17/#19; `ForecastOptions.SignalPlaces`, on). The network carries the profile's usable places (`ForecastNetwork.Places`, `For(profile, timetable, minSamples)`), and the request the sim's signal aspects, track circuits and berths as last reported (`ForecastRequest.LineSide`, `LineSideState`, filled by `LiveState` from signal and track `SG_MSG`s and TD steps). From the timing location a train last reported (its booked point, or an unbooked anchor), the forecast takes the latest of: a **signal** passed since (its place from there); a **track circuit** occupied at or after the train's last report, whose block starts where the train was last reported (the signal before it, or the timing location), if no other running train was last reported there within 2 min (as the learner puts them to trains); a **berth** its headcode stepped into since, if no other live train has that headcode. Each place's share of the run is its fraction between the two timing locations it was learned between, scaled into the run (`LocationShare`). The place used is the one learned for the train's kind of run (departed or passed the first location; stopping at the second if it is the plan's next stop), else any place of that ID between the two: hand-set first, then the most samples (Fred, question 34). The anchor (`ProgressAnchor.Place`, an `AnchorPlace`) replaces an unbooked one. **The rest of the run** is the minimum times the share left, times the train's **pace** in the run so far (time taken ÷ minimum to there, between 1 and `MaxPace` 1.5, measured once it has covered 15 % and 20 s of minimum, and not after a stop), and as for any run no more than the planned rest or the time to the planned arrival. On Waterloo's 4 h recording (places learned from it), forecasts a minute apart put the next timing point 46.9 s from where the train got there on average, against 55.6 s without (2 547 compared; `SignalForecastFixtureTests`).
- **Standing at a signal** (S38; `TrainForecast.Standing`, `StandingAtSignal`). From where the train was last known (the place above, or its timing location), the **signal ahead** is: for a berth, its own signal; after a signal (or a track circuit's block signal), the signal trains passed next after it most often (`SignallingPlace.Next`, learned since S38), if placed in this run; from the timing location, the first placed signal of the trains that took the same line or platform there. The nearest placed signal is not used: parallel lines have signals at almost the same place (Waterloo's S28 on line 5 at 0.291 and S22 on line 2 at 0.302 from Clapham Jn A Jn to Waterloo). The train is standing there if that signal shows red (`LineSide`; without the TD topic, if the train passed the signal before at single yellow) and the train is overdue at it: later than 1.5 × its minimum run there plus 15 s. It is reckoned to have got there at its minimum run (`Since`). The anchor moves to the signal, the train is not `PossiblyStopped`, and the rest of the run is forecast at the minimum from now at the earliest (`Leaves`); the interaction pass holds it behind the train ahead as for any run, so it moves after that train clears rather than now. On the 4 h recording, 54 of 57 trains told as standing next passed that signal from red (the other three took another route at a junction and stood at the signal on it), and 32 of the 44 waits of a minute or more at a signal were found. On the failure recording, the failed T1620 (occupied with no train) is never put to a train.
- **Learning signal places** (S37, #19; `SignalLearner`, `SignalLearning`). Used by the forecast since S38. Fed every gateway event of a live session, replay or review on the session's pump thread (`Observe` keeps reports, track circuit changes and CA steps under a lock), it works out samples when asked (`Learn`, off the UI thread): each train's reports split into **runs** between consecutive timing locations; a run counts if it left a by passing or departing and reached b by passing or arriving, saw no red aspect on approach, and took no more than 1.5 × the fastest run of its kind (through, starting, stopping) over a→b in the session (the WTT's minimums are faster than SimSig's trains run, and left out half the runs). Every non-timing location passed is a signal sample (t − t_a)/(t_b − t_a). Track circuits are put to a train in two sweeps (the place each one's trains were last at, then the one train near at that place), berths by headcode; `03-…md` §6 has how often that works. Every train counts, matched or not. The app pools the samples into the profile (`SignallingPlaces.Learn`, `04-…md` §5) and saves it when the session stops or a replay finishes, and after the profile editor saves; `stringline learn` does the same from recordings.
- **Interaction pass** (Fred: on by default; Plan ▸ Forecast knock-on, since S25). Sections come from the profile's corridors (`ForecastNetwork.For(profile, timetable)`). A section on two corridors is one section, so a branch's trains interact with the main line's. A run is mapped onto the sections between its ends on the first corridor that has both, with the time split by each section's minimum run in that direction. A run no corridor covers is not checked. In each section, a train following another the same way on the same track must enter and leave at least the headway after it. On a single line, an opposing train must have left. **No pair is held further apart than the WTT books them:** when both trains are booked through the section in that order, the spacing is the lesser of the headway and their booked spacing. Opposing trains booked to overlap by up to a minute (crossing-loop rounding) keep that overlap. So the WTT itself makes no knock-on delay: Waterloo's whole day on time gives 8 of 1 768 trains between 4 s and 3 min, where bookings are tighter than the shortest dwells.
- **Tracks side by side.** The profile gives one track each way on a double line, but Waterloo's main line is four tracks. A section is therefore given at least as many tracks each way as the WTT uses at once. Booked runs are put on tracks in entry order: a run entering or leaving within a minute of the last on a track, or overtaking it, takes another track. A following train takes whichever track lets it go soonest.
- **Holding.** A held train waits at its departure point: a pass there becomes a stop. A train already on its way (its departure is actual) is not held, but still occupies the sections.
- **Left out:** cancelled trains, and trains not seen whose plan ended before the session started. A train whose forecast throws is `Unavailable` (logged) and the rest carry on.
- **Not running** (S34, #16; `StartingTrains`, worked out afresh on every forecast from the WTT, `LiveState.SessionStart`, the trains matched live and the plan's run-anyway set, so resume and review agree; it is not a plan command):
  - **Start group:** the seed group (or the timetable's start, for seeded trains with no group) whose start time is the session start, or the latest before it; a group beats the timetable's start at the same time. A session start within 60 s of it is a **fresh start**; anything else is a connection to a sim already running, or a saved game (Fred, S34).
  - **Will not run:** a seeded train of another group (any start); at a fresh start only, an unseeded train booked to come in before the start (its entry time, else its first booked time; no tolerance, from Penrith's 14:00 recording, `04-…md` §1); and a train formed (next working, divide, detach, drop) only from trains that will not run, whatever its own time (Fred, S34). A train formed from one that runs, runs. A train matched live, or run anyway, always runs.
  - Such a train is `TrainForecastStatus.NotRunning` with a `NotRunningReason` ("not seeded", "seed group 04:00", "seeded at 00:00", "formed from 186K") and no points. So it is left out of the forecast layer, conflicts, suggestions, the optimiser and the regulation list, which all take only trains not started or running. The graph draws its WTT line faintly (View ▸ Show not-running trains, or hidden); the train list puts it in a "Not running" group; the delay table counts it apart.
  - **Not seen:** at a fresh start, a seeded train of the start group not seen 2 min after the start is flagged `NotSeen` (it may have been removed). It is still forecast.
  - A replay's `--start` seek plays every earlier frame, so the session start is the recording's first clock. `replay-server --start` pre-rolls before the client connects, so the app sees a later first clock: a late connection, as with SimSig itself.
- **Drawn** (Fred): the forecast layer shows running trains, from their latest actual, and trains not started whose forecast is a minute or more off the plan. On-time future trains show only their plan. Under a minute is on time, as railway delay minutes go: the shortest dwells often differ from the WTT's half-minute bookings by seconds.
- **Measured** (`benchmarks/ --quick`, Release, Waterloo 1 768 trains / 7 834 points half way through the 4× recording): 10 ms independent, 23 ms with the interaction pass (both passes run).

## 3. Conflict detection
Run on the **working plan without the interaction pass** (so conflicts are shown as plan clashes the controller must resolve) and summarise knock-on delay from the forecast.

| Kind | Rule |
|---|---|
| Headway | Two same-direction trains on the same track enter a section less than headway apart, or the follower would arrive at B before leader clears B + headway |
| Overtake | Follower's plan has it reach B before leader on a single track without a loop at A/B |
| Single-line opposing | Opposing occupancy intervals overlap on a single-line section |
| Platform | Two trains occupy the same platform at overlapping times (+ re-occupation margin) |
| Disruption | Plan runs through a blocked section/time |
| Unrealistic | Plan run time < min run time (should be prevented, but imported WTTs may contain it) |

Severity = seconds of delay one of the trains must take to resolve.

*Implemented in S14 (`ConflictDetector.Detect(ConflictRequest)` → `ConflictSet`; `PlanningEngine` runs it after every forecast and publishes it in `PlanSnapshot.Conflicts`).* The rules:
- **Times** (Fred): the forecast **without** the interaction pass (`Forecast.Independent`, which the forecaster now keeps alongside the full one): actuals so far, then the plan with lateness, trains running through each other. A late train shows the clashes its lateness makes, and re-planning a train (holding it, say) clears them. Each conflict carries the train's knock-on from the full forecast (`KnockOnSeconds`).
- **Who gives way.** `Conflict.A` is the train that must take the delay: the one entering the section or platform second, or the one held; `B` the other. `SeveritySeconds` is that delay; `Where`/`When` is where and when A meets it; `To`, `Start` and `End` give the graph its highlight. IDs are stable (kind, trains, place) so the panel keeps its selection.
- **Only what can still be resolved.** A train already on its way into a section (its departure is actual), or already at a platform, is never A, but it is in the way of others. So nothing wholly in the past is reported.
- **Headway, overtake, single line** use the interaction pass's rules, moved into `SectionOccupancy<T>` and shared: each run goes through the sections on its route in entry order; it takes whichever track lets it through soonest; if none does, it clashes with the train in the way on the best one. Overtake is a follower reaching the far end first on the same track. **No pair need be further apart than the WTT books them** (Fred), as in the forecaster. A pair clashing in sections one after another (within 10 min) is one conflict, `Where` to the last `To`, as bad as the worst.
- **Each section's headway** (S27, #7). SimSig's WTT has no headways: SimSig works by signalling, and timetable writers book trains to it. A section's headway is worked out in this order (`Section.ResolveHeadway`):
  1. **Set by hand** in the profile editor (`HeadwaySource.Hand`). It is kept when the corridor is refreshed or regenerated with "Keep mine". Clearing the cell goes back to the automatic value.
  2. **From the WTT** (`HeadwaySource.Wtt`), if it is less than the default. `BookedHeadway.Derive` takes each direction's booked windows through the section (as `CorridorMeasurement` spreads them) and puts them on tracks as the forecaster does. They go in entry order, as many tracks as the WTT needs at once (two runs within 1 min of each other at either end are side by side), and each run goes on the track free longest. A pair's spacing is the lesser of its spacing at the two ends. Pairs more than 30 min apart are not following each other. The figure is the **5th percentile** of the spacings, so one tight pair does not set it. It is at least **1 min** and needs at least **10 pairs**.
  3. **The default:** the profile's default headway (Tools ▸ Edit profile ▸ General), else the global one (Tools ▸ Options ▸ Forecast and conflicts, 3 min).
  - **Only tighten (Fred).** A WTT figure above the default is not used. On a quiet line, trains booked far apart say nothing about how close the signalling lets them run. On Waterloo's Windsor lines beyond Clapham, a WTT figure of 4:30–5:00 made new false conflicts. The corpus (284 WTTs, 12 749 sections on their generated corridors) gives a figure for 10 821 sections. About 1 100 of them (10%) are under 3 min, and most are well over it, so the global default stays 3 min.
  - **Waterloo:** the main line is booked 1:30–2:54 apart (WLOO–INTJN 2:54, NINELMJ–CJML 2:00, EARLSFD–WIMB 1:30). On the 4× recording, headway conflicts at the end fall from 16 to 12, with no new ones. On the failure recording they fall from 3 to 2, and the two clashes the failure causes stay (5S06/5O05 and 2O05/2U07). Llangollen has too few trains following each other, so its single line keeps 3 min.
  - The profile keeps each section's headway, its source, and the WTT's figure and pair count (`bookedHeadwaySeconds`, `bookedHeadwayPairs`, `headwaySource`; profile version 2). In a version 1 profile, a headway other than 3 min was set by hand and stays so; a 3 min one is taken as the default.
  - **Shown:** in the profile editor (Headway and From columns; the From tooltip gives the WTT's figure and pairs), in `stringline corridors` (Headway and From columns; `--headways` lists the WTT's figure and pairs), and in a headway, overtake or single-line conflict's tooltip ("Headway: 2 min 30 s (from the WTT)"; `Conflict.HeadwaySeconds`, `HeadwaySource`).
  - **Observed spacing** (`stringline corridors --headways --log x.sslog`): what trains in a recording actually ran at (`ObservedTimetable`, measured the same way), with the closest pair. It is reported only and never applied: a recording holds an hour or two of trains, so its pairs are few.
- **Platform**: trains planned at the same platform of a location (ignoring case), from arrival to departure (a pass for an instant), must be **1 minute** apart (Fred), or as close as the WTT books them there (even overlapping, as Waterloo shares platforms). Trains associated there (any WTT activity naming the other, or formed from it) are not checked against each other, and a train formed from another holds the platform from the other's arrival (booked and forecast). A platform change gets the full margin.
- **Disruption**: each block the forecast holds a train for (`TrainForecast.BlockHolds`, new); severity is the hold.
- **Unrealistic**: a planned run not yet started shorter than the minimum run, lengthened by speed restrictions in force (the usual case: a restriction added after the plan). The train's own booked run, less allowances, caps the minimum (`MinRunTable.Along(…, ceiling)`), so summed step minimums never flag a WTT run as booked.
- **Threshold** (Fred): clashes under **30 s** are left out (`ConflictOptions.MinSeveritySeconds`): booking rounding.
- **Measured**: Waterloo's on-time day gives 4 conflicts (54 s to 2 min 8 s, where its bookings are tighter than the shortest dwells); detection takes about 9 ms in Release (`benchmarks/ --quick`), 34 ms with both forecast passes.

## 4. Suggestion engine (rule-based v1)
For each conflict, generate candidates:
1. **Hold lower-priority** train at the last location before the conflict where it can wait (station platform, loop, or its origin) until clear + headway.
2. **Swap order** — hold the other train instead.
3. **Alternative platform/line** at the location (from profile platform count; from lines seen in the WTT for that location).
4. For blocks: **hold before the block**, or **terminate short / cancel** (only if user enables "allow cancellation suggestions").

Score = Σ (priority weight × added delay at destination) over all affected trains in a 90-minute forecast horizon, plus penalties for cancellations and platform changes. Re-run the forecaster per candidate (cheap). Offer top 3. Accepting applies the candidate's commands as one undoable step.

*Implemented in S15* (`Suggester.Suggest(SuggestionRequest)` → up to 3 `Suggestion`s, best first; `SuggestionRequest.For(snapshot, conflict)` uses the network and settings the snapshot's forecast was made with, `PlanSnapshot.Settings`). The rules:
- **When** (Fred): worked out for the conflict picked in the list, off the UI thread; again at once when the plan changes, and at most every 2 s as the live state moves on. About 120–500 ms a conflict on Waterloo in Debug.
- **Hold** the train that gives way at the last point at or before where it meets the clash (before it, for a platform) where it can wait and has not yet left: a call (`SetDwell`), a platform it passes (`AddStop`), or its first point (`ShiftTrain` from there). The hold starts at the conflict's severity from its forecast departure (from before a block's hold, if a block holds it there), to the next half minute; if the forecast with it still has the pair clashing (the train makes up time on the way), what is missing is added, up to 4 times and 2 h.
- **Swap**: the same hold for the other train, until the first has gone ahead with its spacing (on a single line it waits at the far end). Not offered if it cannot wait before the clash (already on its way, or formed in the platform).
- **Platform** (platform conflicts): up to 3 other platforms used at the location (by any train in the plan) that are free while the train would be there, nearest the booked number first. A train formed in the platform from it moves with it; a train formed there from another brings that one too, and is not moved once that one is in.
- **Block**: the hold planned; for a block on one WTT line, up to 3 other lines out of the location; and only if the user allows it (off by default, remembered), terminate short at the last stop before it, or cancel a train not yet started.
- **Run time** (unrealistic): `ShiftTrain` from the end of the run by what it is short of.
- **Score** (lower is better) = Σ weight × (the train's forecast time with it − without it) at each train's last point still to come within 90 min, with the knock-on pass if it is on. Weight = category priority / 50 (Fred), at least 0.1; 50 if the profile has none. So planning a hold the knock-on forecast already has costs nothing, and a train that gains counts against the cost. Plus a penalty: 2 min for a platform or line change, 30 min for terminating short, 60 min for cancelling. Plus weight × severity of each **new platform clash** (the forecast does not hold trains for platforms), or of every new clash with the knock-on pass off.
- **Order**: those that resolve the conflict (this pair no longer clashes in this way at this place; or the train is no longer held by the block, or planned too fast) first, then score. Each reports the conflicts it clears and adds, its impacts per train, the trains it changes and the plan with it applied (for the preview).
- **Applying** is `AcceptSuggestion` with the suggestion's description as its `Title` ("Suggestion: Hold 1F01 at A until 08:07 (+2 min)" in the history). The app refuses to apply one worked out on an older plan (a shift is relative).
- **Not yet**: line changes for headway clashes (the sections pick tracks themselves, so a line change makes no difference to the forecast there); holding at a signal or loop the WTT does not time.
- **Signal places for holding (S37, for S33).** S37's gate passed on Waterloo: learned places are stable between recordings (`03-…md` §6), so S33 can offer holds at used signals. Kings Cross (where #17 showed) is still to check with a `--td` recording.

## 5. Later: optimiser (C)
Rolling-horizon MILP/CP over the next 60–90 min within the corridor using Google OR-Tools CP-SAT: decision variables are section entry times and order binaries per conflicting pair; objective weighted delay; constraints headway/single-line/platform/min-run. Outputs a command set for preview. Kept behind an interface `IReplanner` so v1 rules and the optimiser are interchangeable.

*Built in S20.* Fred chose: OR-Tools CP-SAT (in its own project, `Stringline.Optimiser`); holds **and** platform changes; the Plan menu over the whole horizon (`05-…md` §15); 60 min and 5 s by default, both in Options.
- **The interface** (`Stringline.Planning`): `IReplanner.Replan(ReplanRequest)` → `ReplanResult`. The result has:
  - the commands and the steps (`ReplanStep`: a hold or swap with when the train now leaves, or a platform or line change);
  - the conflicts in the horizon before and after, and how many it clears and adds;
  - the weighted delay, impacts, penalty and changed trains, and the plan with it, as for suggestions;
  - the rounds, whether the last model was solved optimally, and the time taken.

  `ToCommand()` is one `AcceptSuggestion` titled "Re-plan to 09:05: 4 holds, 1 platform change". `ReplanEvaluator` is shared by both re-planners: it applies a candidate set of commands, forecasts and checks it as the engine would (with the knock-on pass if on), and scores it.
- **Better** (`ReplanCandidate.BetterThan`) means fewer conflicts in the horizon; then less weighted severity (Σ weight × severity); then less weighted delay plus penalty. Delay is measured as for suggestions: at each train's last point in the horizon, against the plan's forecast. A result is `Improved` only if it is better than the plan as it stands; else `NoImprovement` (or `NoConflicts`), with no commands.
- **Which conflicts.** Clashes between two trains: headway, overtake, single line and platform, with `When` up to the horizon's end. Blocks and runs planned too fast are about one train and stay with their own suggestions.
- **Rules** (`RuleReplanner`): the earliest such conflict not yet tried gets its suggestions (§4, with the re-plan's step, hold limit and penalties; never cancelling). The first that resolves it and leaves the plan better is applied. Then the next, until none is left, 40 steps, or the time limit.
- **Optimiser** (`CpSatReplanner`, `ReplanModel`).
  - **Trains.** Every train not finished with a forecast time up to the horizon, from its latest actual to its first timed point past the horizon. The model's times follow the plan builder and the forecaster exactly, so with the same holds it gives the same times (`ReplanModelTests`):
    - a run takes `max(min, min(planned run, planned arrival − departure))`;
    - a stop's departure is the later of arrival + dwell and the planned departure;
    - a train formed from another starts after it arrives plus the turnaround;
    - a hold changes the **plan**: later points move on only as far as minimum runs need, keeping their booked dwells (§1), and the forecaster never runs the train before its plan. So a held train makes up time on run allowances, not at stops.
  - **Holds** are where suggestions hold: a call (`SetDwell`), a platform passed (`AddStop`, with the forecaster's dwell), the first point (`SetDwell`, less any sim entry delay; entering the area, `ShiftTrain`). They are rounded up to the half minute.
  - **Platforms.** A train at a platform clash may move to up to 3 other platforms used there that are free while it is there (`PlatformCandidates`, nearest number first). A train formed there from another, or forming one there, moves with it. It cannot move once it, or the train it is formed from, is there.
  - **Orders.** Each pair that clashes, and each of their trains' neighbours on their routes (the trains either side in each section with one track that way, opposing trains on a single line, and either side at their platforms), gets an either-or order with the detector's spacing. The spacing comes from `SectionOccupancy`: in a section, the headway at both ends, or as close as the WTT books them; on a single line, after the other has cleared; at a platform, the margin, or as booked. A section's entry and exit are shares of the run, as the forecaster splits it. Clashes under the least conflict reported are allowed, as the detector allows them.
    - On a section with **more than one track** that way, a side needs spacing only once the detector finds the pair clashing that way round. Until then it only keeps the order, as the train behind may take another track.
    - At a platform, an order applies only while both trains are planned there.
    - A pair the model cannot keep apart (both trains already running) costs 100 weighted seconds a second, so the model is always solvable.
  - **Cost** (minimised, tenths of weighted seconds): Σ weight × delay at each train's last point in the model; 0.2 × weight a second held (a train that makes up time is still late on the way, so the shortest, latest hold wins); 15 × weight a hold; the platform change penalty (2 min) a move.
  - **Rounds.** Up to 6 rounds within 80% of the time limit. Each round solves the model (hinted with the last solution), turns it into commands, and checks them with the forecaster and conflict detector, which have the last word. Each conflict still found becomes an order, with its trains' neighbours. A pair that still clashes as the model planned it gets the shortfall as more spacing on the side chosen. The best plan checked is kept.
  - **Pruning.** In the time left, each step is dropped in turn, smallest hold first, if the plan without it is no worse. A solution found under a time limit, or rounded to the half minute, can otherwise hold trains for nothing.
  - **Threads**: as many as the machine has, up to 8 (`ReplanOptions.Workers`; 1 makes the solver deterministic). With several threads and a time limit, a busy horizon's plan can differ from run to run.
- **Measured** (Debug, this machine, 5 s): see `progress.md`, S20. Waterloo's 4× recording half way (2 conflicts): both clear them; the optimiser holds 6L49 3 min for −150 weighted s, the rules −90. The failure recording (4): both leave 1 (a block's train already running) for no delay. The 4× recording at its end (21 conflicts, most at Waterloo's platforms with trains arriving now): the optimiser 21 → 12–18, the rules 21 → 16.
- **Not built:** line changes; holding at signals; cancelling or terminating short; a whole train's re-route. The rules' result is not used to polish the optimiser's.
